# Q450: CUDA Graph 与 Tensor Parallelism (TP) 融合通信挂死定位：在大模型分布式场景中开启 CUDA Graph 与 TP 出现卡死（Hang），为何关闭 Graph 或降 TP 仅是定位线索而非根因？如何通过最小变量矩阵与 Trace 工具排查？通信状态标记（flag）内存位置、内存模型与同步协议如何设计？修复验证方案应包含哪些维度？

> [!QUESTION] 问题描述
> CUDA Graph 与 TP 融合通信卡死定位：在大模型训练/推理开启 CUDA Graph 且 TP > 1 时出现进程死锁/卡死（Hang），为什么关闭 Graph 或将 TP 降为 1 现象消失只是“定位线索”而非“根因结论”？如何通过变量矩阵与 Profiler/Trace 工具逐步排查至融合通信算子？通信状态标记（flag）存放在何处、为何选用浮点类型、其内存一致性与同步协议在原实现中如何设计？修复后如何通过最小复现用例与模型级端到端回归进行验证？

> [!SUCCESS] 通用参考与审查要点
> - **核心机制与假设**: CUDA Graph 固化 GPU 工作流与依赖，捕获阶段不能捕获任意动态主机控制流；TP 通信挂死常源于跨 rank 通信发起顺序不一致或静态工作捕获跨 rank 依赖。
> - **证据要求**: 检查跨 rank 同步机制选型，确认通信 flag 是否具备正确的内存顺序、可见性与生命周期管理（普通浮点 load/store 不因类型提供协议正确性；部分浮点具备 atomic 支持，需看具体选型与同步原语）；查验 NCCL 流同步与事件记录。
> - **排查与追问**: 使用 Nsight Systems 结合 NCCL_DEBUG=INFO 抓取各 rank 关键路径与停顿事件；追问拓扑对称性与超时复现边界。
