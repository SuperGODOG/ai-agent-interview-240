## 1. 30 秒项目介绍 (Elevator Pitch)

本项目是一套基于 **Python (FastAPI + Redis + RabbitMQ + MySQL)** 原生实现的生产级高并发秒杀交易核心后端。

针对瞬时极端突发流量场景，系统构建了**“漏斗式多层截流”**与**“异步化削峰落库”**链路：
- **入口层**：通过基于 Redis Lua 的原子令牌桶实现单用户毫秒级限流拦截；
- **缓存层**：采用 Redis Lua 脚本一次性完成“原子买家去重集合查验 + 库存原子预扣 + 预扣凭证（Reservation Hash）暂存”，提供结构化契约返回；
- **削峰层**：通过 RabbitMQ 开启 Publisher Confirms（发布确认）模式可靠衔接异步消息；
- **持久化防线**：独立消费者拉取消息，在 MySQL 单本地事务内通过**单 SQL 条件更新（当前读行级 X 锁）**与 **`(user_id, goods_id)` 联合唯一索引**作为存储层绝对底线；
- **容灾底座**：设计**双层对账引擎（Reconciliation Service）**，支持**管理后台/运维按需手工触发对账巡检**，通过对齐物理落单真实事实，安全纠偏悬挂 Reservation 与幽灵预扣，彻底收敛分布式网络下的掉单与不一致窗口。

## 2. 核心架构哲学与面试钩子 (Architecture Philosophy & Hooks)

### 核心架构哲学
在高并发在线交易链路中，**“放弃跨 Redis、RabbitMQ、MySQL 的全局 2PC 强一致性幻想，换取极致的低延迟与高吞吐”**。系统通过**“局部原子性 + 幂等可恢复 + 状态 CAS + 活动后手工双层对账”**，把由于极端断网或崩溃导致的分布式不确定性，收敛为**“可发现、可定位、可人工/脚本安全修复”**的工程确定性闭环。

### 两个关键面试钩子（攻克分布式系统的两个“不确定性窗口”）
1. **不确定性窗口 1（发布歧义：Redis 扣减成功但 MQ 发送未决）**：
   - *问题*：Redis 预扣了库存并记录了买家集合，但调用 MQ 发送时网络超时或连接断开。
   - *面试防守关键*：**绝不能声称“立即回滚 Redis 是绝对安全的”！**
     - 因为网络超时并不代表 Broker 没有收到消息；若消息已物理入队且被下游消费者落库，API 层若盲目 `INCR` 回补 Redis，就会导致**超卖（库存多回补一次）**和**买家防重集合失效（一人可多次下单）**。
     - *当前工程取舍*：API 捕获发送异常时做保护性快速失败，保留带时间戳的 `reservation_id` 悬挂凭证；在活动结束后，**由运维手工触发双层对账**，以 MySQL 物理落单事实为基准进行安全核实与回补。
2. **不确定性窗口 2（消费中断：MySQL 落库成功但 MQ ACK 丢失）**：
   - *问题*：消费端在 MySQL 成功落单并提交事务，但在向 RabbitMQ 发送 ACK 前消费者崩溃或网络闪断，导致消息重新投递。
   - *解法*：MySQL 存储层建立 `(user_id, goods_id)` **联合唯一索引硬防线**，单 SQL 扣减以 `stock_count > 0` 条件更新。重复消息被消费时，前置查询或唯一索引冲突（IntegrityError 1062）均会安全幂等拦截，对齐 Redis 状态为 `ORDER_CREATED` 后正常返回 ACK，保证业务绝对不超卖、不重复落单。

## 3. 框架原生默认 vs 自研核心设计 (Framework vs My Custom Design)

| 模块 | 框架/中间件提供什么 | 我独立设计的核心机制 |
|---|---|---|
| **请求准入与限流** | FastAPI 路由与依赖注入、Pydantic 请求校验 | 基于 Redis Lua 原生实现的**原子令牌桶算法**，避免高并发下并发读写漂移与穿透 |
| **库存预扣与防重** | Redis 原生 `DECR`、`SADD` 基础指令 | 自研 **`stock_deduct.lua` 结构化三元组原子契约**：单次网络 RTT 内完成防重、查库、预扣、暂存 Hash，杜绝并发竞争条件 |
| **异步削峰与消息可靠性** | RabbitMQ 默认轮询转发与基础推送 | 启用 **Publisher Confirms** 可靠发布确认机制与持久化消息投递，显式捕获发布歧义 |
| **持久化与事务保障** | SQLAlchemy ORM 基础映射、MySQL InnoDB | **单 SQL 条件更新**（`WHERE stock_count > 0` 依赖当前读 X 锁）替代悲观锁，联合唯一索引兜底防穿透 |
| **系统对账与容灾修复** | 无（主流秒杀项目普遍缺失） | 自研 **双层对账引擎（Reconciliation Service）**：层级 1 物理守恒检验 + 层级 2 悬挂 Reservation **手工按需触发巡检修复**（非后台定时常驻） |

## 5. 架构演进设定与待验证边界（面试求真声明）

1. **未实装字段明确声明**：
   - 当前核心表 `order_info` 和 `miaosha_order` 仅包含 `goods_id`、`user_id`、`order_no` 等必要物理字段；
   - **`activity_id`、`sku_id`、`request_id` 在当前代码中均不存在且未落库**，不得虚构为已实现。多活动场景下的 `(user_id, activity_id, goods_id)` 联合键作为【面试设计演进设定】。
2. **全链路 Request ID 染色**：【面试设计设定】当前系统在内存与消息体中通过 `event_id` 与 `reservation_id` 串联业务追踪；端到端分布式链路染色（MDC / OpenTelemetry TraceContext）作为生产级监控演进方向。
3. **压测与 QPS 指标求真声明**：【待实机基准压测验证】系统在单机/容器环境下未经严密隔离的真实压测前，**不宣称已实现 1000 QPS 或更高吞吐数字**；以架构设计合理性与数据库物理守恒断言为准，绝不虚构性能结论。
