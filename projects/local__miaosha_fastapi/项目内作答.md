### L177
- **题目**：在构建生产环境的 Agent 系统时，如何设计内存与状态的多级存储方案？针对短期会话上下文、长期记忆以及结构化用户画像，你会分别选择什么类型的存储介质（如 KV 缓存、向量数据库、关系型数据库），其背后的选型考量是什么？
- **深度分类**：`[二_Agent应用开发相关/5.agent记忆设计 d4]`
- **核心结论（一句话面试回答）**：
  生产交易与状态系统的多级存储选型遵循**“读写性能与数据持久化强一致性的权衡”**：用内存 KV 承担毫秒级突发吞吐与原子预留，用持久化队列承担削峰缓冲，用关系型数据库沉淀终态法律账务事实。
- **展开细节（面试追问点）**：
  1. **第一级：内存 KV（Redis）——毫秒级瞬时预扣与防重过滤**：
     - 介质：Redis 单线程内存模型。
     - 存储结构：
       - `miaosha:stock:{goods_id}`（String）：物理库存计数，通过 Lua 原子 DECR；
       - `miaosha:buyers:{goods_id}`（Set）：已购买用户名单集合，通过 `SISMEMBER` / `SADD` 毫秒级阻断同一用户重复秒杀；
       - `miaosha:reservation:{goods_id}:{user_id}`（Hash）：短期预扣凭证，记录 `status="PENDING"` 与过期时间（TTL 1800s）。
     - 选型原因：全内存轻量执行，避免瞬时高并发写入穿透直接冲击数据库磁盘 I/O（未验证具体 QPS 吞吐，核心价值在于架构分层减压）。
  2. **第二级：消息中间件（RabbitMQ）——持久化缓冲解耦**：
     - 介质：磁盘物理持久化队列（`durable=True`, `delivery_mode=2`）。
     - 选型原因：平滑吞吐毛刺，将秒杀峰值流量以恒定消费速率导入下游数据库，防止连接池耗尽。
  3. **第三级：关系型数据库（MySQL InnoDB）——ACID 终态持久化防线**：
     - 介质：MySQL 8.0 InnoDB 引擎。
     - 存储结构：`order_info`（主订单表）与 `miaosha_order`（秒杀关联表）。
     - 选型原因：具备成熟的 WAL、Redo Log 与行级锁机制，支持复合唯一索引约束，是法律与账务事实的最终真实来源（Source of Truth）。
  4. **追问防守：为什么不在 Redis 里直接生成并维护最终订单？**：
     - 答：Redis 的 RDB/AOF 机制在极端断电下存在微秒级丢数据风险；且 Redis 不支持复杂关系型外键与 ACID 严格约束，难以支撑后续的财务审计、退款流转与订单报表分析。

### L188
- **题目**：在多模态与异步事件输入（包含语音、文本及外部工具回调）的场景下，如何设计Agent的复杂状态机以保证状态的一致性与稳定性？
- **深度分类**：`[二_Agent应用开发相关/6.agent处理情景的架构设计 d3]`
- **核心结论（一句话面试回答）**：
  面对 MQ 异步重投、并发回调与网络抖动等异步事件，系统状态机必须遵循**“单向不可逆迁移、带前置幂等拦截与数据库 CAS 条件更新”**三大原则。
- **展开细节（面试追问点）**：
  1. **全生命周期单向状态流转**：
     - `RESERVING (PENDING)`：Redis Lua 预扣成功，凭证暂存；
     - `QUEUING`：RabbitMQ Publisher Confirms 投递成功，消息排队中；
     - `UNPAID`：MySQL 事务落单成功，生成 `OrderInfo`，Redis 预扣状态原子对齐为 `ORDER_CREATED`；
     - `PAID`：外部支付回调事件驱动，执行 CAS 条件更新（`status='UNPAID' -> 'PAID'`）；
     - `CANCELLED / FAILED`：支付超时未付款或扣减失败，单向流转至取消终态，触发库存回补，不可逆转。
  2. **消费端异步事件幂等处理**：
     - 当网络断开导致 MQ 重新投递（Redelivery）或并发多次消费相同消息时：
       - *第一步*：查验 MySQL 中是否存在该 `(user_id, goods_id)` 的 `MiaoshaOrder`；
       - *第二步*：若已存在，直接命中幂等逻辑，刷新 Redis 状态为 `ORDER_CREATED`，返回成功 ACK，绝不重复扣减库存；
       - *第三步*：若并发绕过前置查验，MySQL 联合唯一键 `uq_user_goods` 抛出 `IntegrityError 1062`，事务自动回滚，保障数据一致性。
  3. **追问防守：若支付成功事件与超时取消事件并发到达，如何防范状态错乱？**：
     - 答：采用版本号或单向状态条件判断：`UPDATE order_info SET status='CANCELLED' WHERE id=:id AND status='UNPAID'`。若支付回调已先一步将状态改为 `PAID`，取消更新的 `rowcount == 0`，自动阻断非法取消，避免将已付订单错误关单。

### L237
- **题目**：在工程落地中，有哪些具体的工程化手段（如重试机制、状态机控制、幻觉拦截等）可以保障商用Agent框架的稳定性和鲁棒性？
- **深度分类**：`[二_Agent应用开发相关/8.工程落地 d4]`
- **核心结论（一句话面试回答）**：
  保障高并发与分布式交易系统鲁棒性的核心工程手段，在于**“将跨系统网络不确定性显式化，通过前置拦截、局部原子性、审慎处理发布歧义与管理后台手工触发对账形成完整闭环”**。
- **展开细节（面试追问点）**：
  1. **不确定性窗口 1 的工程深挖：为什么不能声称‘立即回滚是绝对安全的’？**：
     - *现象*：Redis Lua 预扣库存与买家集合成功，但在向 RabbitMQ 投递下单事件时发生网络超时或断开连接。
     - *深度风险防守*：
       - 当网络通信发生超时或抛出未决异常时，**该消息可能已经成功穿透并抵达 Broker，甚至已被下游消费者消费落库**！
       - 若 API 层盲目判定为失败并立即执行 `rollback_redis_reservation`（`INCR stock` + `SREM buyers`），一旦那条消息最终成功在 MySQL 创建订单，就会导致**严重的超卖（Redis 凭空多出可售库存）**以及**限购失效（买家集合被清除，该用户可再次抢购）**！
       - *当前系统的工程权衡*：代码中在捕获显式异常后做回补尝试属于可用性优先的折中，但绝非万无一失；系统在此处保留了带时间戳的 `reservation_id` 状态记录，**真正的安全底线依赖活动结束后由运维手工触发双层对账**，以 MySQL 真实落库记录为最终依据来决定是否真正回补库存。
  2. **不确定性窗口 2 的工程防御：消费端幂等与联合唯一约束**：
     - *现象*：消费端在 MySQL 完成单本地事务扣减与建单后，向 RabbitMQ 回传 ACK 时网络抖动，Broker 判定超时重投。
     - *手段*：利用数据库 `(user_id, goods_id)` 联合唯一键 `uq_user_goods` 作为物理铁律；重投消息再次进入时，前置查询或唯一索引冲突（`IntegrityError 1062`）拦截重入，对齐 Redis 状态为 `ORDER_CREATED` 后直接确认丢弃，确保绝对不发生二次扣款或重复下单。
  3. **终极托底机制：双层对账引擎（Reconciliation Service，管理后台按需手工触发）**：
     - 系统并未引入定时常驻的后台自动任务（防止在秒杀高并发期间误杀在途消息或争抢数据库连接池）；
     - 而是在秒杀活动结束后，**由管理后台或运维人员手工按需触发**：
       - 扫描处于 `status="PENDING"` 且存活时间超过阈值（如 60 秒）的悬挂单；
       - 若 MySQL 中已存在订单（落库成功但 Redis 状态未对齐），手动对齐 Redis 状态为 `ORDER_CREATED`；
       - 若 MySQL 中查无此单（确认消息丢失未落库），才安全执行 Redis 库存回补与买家标记移除。

### L39
- **题目**：如何构建 Agent 的效果评估体系（Evaluation Framework）？有哪些主流的 Benchmark 维度？是依赖人工标注、LLM-as-a-judge还是线上业务指标？
- **深度分类**：`[二_Agent应用开发相关/9.业务评估(性能优化与诊断) d3]`
- **核心结论（一句话面试回答）**：
  在秒杀与交易核心系统中，评估体系的第一准则是**“物理不变量守恒断言”**，以硬性数据一致性验证为绝对先验，辅以并发吞吐、延迟分布与手工对账修复时效构建立体评测基准。
- **展开细节（面试追问点）**：
  1. **正确性第一守恒定律（物理断言）**：
     - 在无人工补库存、无退款取消的基准测试运行后，必须满足断言：
       $$\text{初始 MySQL 库存} = \text{最终 MySQL 库存} + \text{成功落单数量}$$
     - 物理库存绝对下限断言：$\text{库存} \ge 0$，严禁出现负库存；

### L319
- **题目**：请介绍 HTTP 状态码 503 和 504 的具体含义、区别及常见产生原因。
- **深度分类**：`[四_八股相关/2.计算机网络与通讯协议 d1]`
- **核心结论（一句话面试回答）**：
  503（Service Unavailable）代表服务器当前因过载或维护而**主动拒绝服务**（如限流熔断），客户端可明确知晓未被执行；504（Gateway Timeout）代表网关作为代理**等待上游响应超时**，其本质是分布式网络中的**状态未决（歧义窗口）**。
- **展开细节（面试追问点）**：
  1. **503 与 504 核心区别与根因对比**：
     - **HTTP 503 Service Unavailable**：
       - *含义*：服务端当前暂时无法提供服务，通常是由于瞬时并发请求远超系统承载上限，触发了保护性截流。
       - *在秒杀场景的映射*：网关层或 FastAPI 依赖注入层触发令牌桶限流（如 `check_rate_limit` 抛出 429/503），或后端数据库连接池满保护性熔断。
       - *业务影响*：确定性强，服务端并未执行扣减，客户端可通过指数退避或引导稍后重试。
     - **HTTP 504 Gateway Timeout**：
       - *含义*：作为网关（如 Nginx、API Gateway）的服务器在转发请求后，未在规定超时时间内收到上游后端应用的响应。
       - *在秒杀场景的映射*：高并发下后端 Python 事件循环被阻塞、数据库行锁严重排队等待，或 MQ 投递过程网络丢包导致请求悬挂。
       - *业务影响*：**状态严重未决**。上游可能已经预扣了库存甚至落了库，仅仅是响应数据包在网络中超时。
  2. **应对与架构设计考量**：
     - 遇到 503：客户端执行随机退避重试（Jittered Backoff）或展示“排队人潮拥挤”；
     - 遇到 504：前端**绝不能直接提示“秒杀失败”**，更不能放任用户无脑连续点击重试，而应自动引导进入订单轮询查验流程，后端依托发布确认异常处理与手工对账机制收敛歧义。
- **证据锚点**：

### L473
- **题目**：Redis 加 Lua 脚本去扣减库存了之后，消息如果发送失败了会怎么样？开启消息重试机制，那重试也失败了呢？

     - 若发送消息或等待 ACK 时发生网络闪断/超时，该消息很有可能已经物理进入 RabbitMQ 队列，且正被下游消费者消费并提交到 MySQL！

### L409
- **题目**：DB 扣了十条库存而 Redis 显示扣了十二条，能否直接认定有两条失败？如何建立对账证据？
- **深度分类**：`[一_业务与项目实战/秒杀业务实战 d4]`
- **核心结论（一句话面试回答）**：
  **绝对不能直接认定失败，更严禁直接用 DB 库存覆盖 Redis！** 差额可能由“在途消息排队延迟”或“真实丢单”引起，必须建立包含 `reservation_id` 的完整审计证据链，在活动排空后手工触发比对。
- **展开细节（面试追问点）**：
  1. **为什么严禁用 DB 库存暴力覆盖 Redis？**：
     - 若秒杀仍在进行或队列中尚有积压，多扣的两条库存可能正是处于 MQ 消费排队中的在途请求；
     - 若粗暴将 Redis 库存改为 DB 剩余值，这部分在途请求后续消费落库时，就会导致 Redis 库存与实际物理库存彻底脱节，引发超卖或系统震荡。
  2. **如何建立对账证据链？**：
     - 依据 `stock_deduct.lua` 在预扣阶段写入的 Hash 结构：`miaosha:reservation:{goods_id}:{user_id}`，内含 `user_id`、`created_at`、`status="PENDING"` 与唯一 `reservation_id`；
     - 对账流程：
       1. 确保活动已结束、MQ 队列已无积压；
       2. 扫描存活时间超过阈值（如 60s）且状态仍为 `PENDING` 的悬挂键；
       3. 拿这些键的 `user_id` 去 MySQL `miaosha_order` 表中查验；
       4. 若 MySQL 中已有订单记录，说明仅仅是状态未回写，将 Redis 状态对齐为 `ORDER_CREATED`；
       5. 若 MySQL 中确定无单，说明消息在中途丢失或崩溃，此时才确凿证实为失败，安全调用 `rollback_redis_reservation` 回补库存。
