# 0023 · AQS 详解（★核心）

这一课覆盖 。**AQS（AbstractQueuedSynchronizer）** 是 Doug Lea 一手打造的 *JUC 半壁江山*：`ReentrantLock`、`ReentrantReadWriteLock`、`Semaphore`、`CountDownLatch`、`ThreadPoolExecutor` 的 Worker 全都建立在它之上。搞懂 AQS，等于同时搞懂了这一堆 JUC 类。

## 学前热身

Warm-up · 凭直觉答一下

<details>

<summary>Q0.1 AQS 的 `state` 变量存什么？</summary>

语义由子类定义：`ReentrantLock` 存重入次数、`Semaphore` 存剩余许可、`CountDownLatch` 存倒计数、`ReentrantReadWriteLock` 高 16 位存读锁计数低 16 位存写锁计数。AQS 只负责用 CAS 原子地更新它。第 2、8 题细讲。

</details>

<details>

<summary>Q0.2 AQS 的 CLH 队列是什么数据结构？</summary>

改造后的 **双向**链表（原始 CLH 是单向自旋队列）。每个节点是一个等待线程；线程被 `park` 挂起而非纯自旋，避免烧 CPU。第 3 题细讲。

</details>

## 面试场景 1：AQS 是什么？为什么要有它？（★核心）

🎤 面试官

介绍一下 AQS。

🧑‍💻 你

`AbstractQueuedSynchronizer` 是一个**抽象类**，位于 `java.util.concurrent.locks`。它给「同步器」（锁、信号量、闭锁）提供了通用骨架 —— 通用的*排队、阻塞、唤醒*逻辑，AQS 都写好了；*子类只需实现「资源怎么获取释放」*这一小段业务代码。

可以类比模板方法设计模式：AQS 定义了 `acquire` / `release` 的整体流程，把「怎么算获取成功」这一步留给子类的 `tryAcquire` / `tryRelease` 实现。所以从这一个抽象类，长出了 `ReentrantLock`、`Semaphore`、`CountDownLatch`、`ReentrantReadWriteLock`、`CyclicBarrier`（借道）、`ThreadPoolExecutor.Worker` 一大票同步器。

追问 为什么 Doug Lea 要抽象出 AQS？直接每个同步器各自写不行吗？

**去重复 + 保证质量**。锁、信号量、闭锁虽然语义不同，但底层都要做「一个变量表示状态 + 线程排队 + park/unpark 挂起唤醒」这三件事。把它们抽出来放进 AQS，每个同步器只关心自己的语义，实现极简（`ReentrantLock` 的 `Sync` 内部类才几十行），且享受 AQS 精心优化的排队/唤醒逻辑。

## 面试场景 2：AQS 的核心字段（★核心）

🧑‍💻 你

```
public abstract class AbstractQueuedSynchronizer
extends AbstractOwnableSynchronizer {

private volatile int state;              // 同步状态，语义由子类定
private transient volatile Node head;    // CLH 队列头
private transient volatile Node tail;    // CLH 队列尾

// 由父类 AbstractOwnableSynchronizer 提供
private transient Thread exclusiveOwnerThread;   // 独占模式下的持锁线程

// 只提供三个操作 state 的方法
protected final int getState() { return state; }
protected final void setState(int newState) { this.state = newState; }
protected final boolean compareAndSetState(int expect, int update) {
return STATE.compareAndSet(this, expect, update);   // CAS
}
}
```

就三个关键字段：

- **`state`**：`volatile int`，通过 CAS 更新。*语义完全由子类定义*：

- `ReentrantLock`：state = 重入计数（0 表示未被持有；1 表示被持有一次；n 表示重入 n 次）

- `Semaphore`：state = 剩余许可数

- `CountDownLatch`：state = 倒计数（0 表示门开了）

- `ReentrantReadWriteLock`：state 高 16 位 = 读锁持有数，低 16 位 = 写锁持有数

- **`head` / `tail`**：CLH 双向队列的头尾指针。

- **`exclusiveOwnerThread`**：独占模式记录当前持锁线程 —— 用于可重入判断和 `isHeldExclusively`。

## 面试场景 3：CLH 队列结构 & Node 的 waitStatus（★核心）

🧑‍💻 你

AQS 的 CLH 是*「自旋 + 阻塞」的改进版双向链表*（原始 CLH 是纯自旋单向）。每个节点结构：

```
static final class Node {
volatile Thread thread;         // 排队的线程
volatile Node prev;             // 前驱
volatile Node next;             // 后继
volatile int waitStatus;        // 节点状态（下面 5 种）
Node nextWaiter;                // Condition 队列指针或共享模式标记
}
```

`waitStatus`值含义

**SIGNAL**-1「后继需要被唤醒」—— 我释放时要 `unpark` next
**CANCELLED**1「节点已取消」—— 因中断或超时；不再参与竞争，会被跳过
**CONDITION**-2「在 Condition 队列上等待」—— 被 signal 后转移到 CLH
**PROPAGATE**-3「共享模式下唤醒需向后传播」—— 解决共享模式的信号丢失
初始0新节点默认值

陷阱 `waitStatus` 是*「本节点对后继的承诺」*而不是「本节点自己的状态」。SIGNAL 的意思是「我（前驱）欠后继一次唤醒」，所以「shouldParkAfterFailedAcquire」检查的是*前驱的 waitStatus*，如果前驱是 SIGNAL 才能安心 park。

## 面试场景 4：模板方法设计（★核心）

🧑‍💻 你

AQS 提供 4 个模板方法（final）供子类调用：

- `acquire(int arg)` —— 独占获取，不响应中断

- `release(int arg)` —— 独占释放

- `acquireShared(int arg)` —— 共享获取

- `releaseShared(int arg)` —— 共享释放

子类只需重写下面 5 个钩子（默认抛 `UnsupportedOperationException`）：

- `tryAcquire(int arg)` —— 独占尝试获取（成功返回 true）

- `tryRelease(int arg)` —— 独占尝试释放（成功返回 true）

- `tryAcquireShared(int arg)` —— 共享尝试获取（返回剩余资源数）

- `tryReleaseShared(int arg)` —— 共享尝试释放（是否影响后继）

- `isHeldExclusively()` —— Condition 用

比如 `ReentrantLock` 只需重写 `tryAcquire/tryRelease`，其他排队/阻塞/唤醒逻辑全部复用 AQS 的现成实现。

## 面试场景 5：独占模式 acquire 完整流程（★背下来）

🧑‍💻 你

```
public final void acquire(int arg) {
if (!tryAcquire(arg) &&
acquireQueued(addWaiter(Node.EXCLUSIVE), arg))
selfInterrupt();
}
```

四步走：

1. **`tryAcquire(arg)`**：子类实现的「尝试获取」逻辑。ReentrantLock 里就是「state==0 就 CAS 成 1；state>0 且持有者是我就重入 +1」。成功直接返回。

2. **`addWaiter(EXCLUSIVE)`**：失败 → 创建 Node 加入 CLH 队尾。用 CAS `compareAndSetTail`；失败就走 `enq` 全自旋直到入队。

3. **`acquireQueued(node, arg)`**：入队后自旋。

- 如果*我的前驱是 head*（说明我是第一个候选） → 再 `tryAcquire`，成功就把自己设为 head 返回。

- 否则 `shouldParkAfterFailedAcquire`：把前驱 waitStatus 设为 SIGNAL（承诺唤醒我），跳过 CANCELLED 的前驱。

- 然后 `parkAndCheckInterrupt`：`LockSupport.park(this)` 挂起线程，直到被 `unpark`。

4. **`selfInterrupt`**：如果获取过程中收到过中断（park 期间被 interrupt 会返回 true），出来后补一次中断标志（因为 acquire 不响应中断，但要让上层知道曾被打扰过）。

## 面试场景 6：独占模式 release 流程

🧑‍💻 你

```
public final boolean release(int arg) {
if (tryRelease(arg)) {                       // ① 子类逻辑：state -= arg，是否完全释放
Node h = head;
if (h != null && h.waitStatus != 0)
unparkSuccessor(h);                   // ② 唤醒后继
return true;
}
return false;
}

private void unparkSuccessor(Node node) {
// 清 head 状态
if (node.waitStatus < 0) compareAndSetWaitStatus(node, node.waitStatus, 0);

Node s = node.next;
if (s == null || s.waitStatus > 0) {          // s 是 null 或 CANCELLED
s = null;
// ★ 从 tail 往前遍历找最靠前的正常节点
for (Node t = tail; t != null && t != node; t = t.prev)
if (t.waitStatus <= 0) s = t;
}
if (s != null) LockSupport.unpark(s.thread);
}
```

追问 为什么 `unparkSuccessor` 要**从 tail 往前**遍历？直接 `node.next` 不好吗？

因为 `addWaiter` 入队**不是完全原子**：先 CAS `tail`，再设 `tail.prev.next = newNode`。这两步中间可能被别的线程读到「新节点的 `prev` 已经指向老 tail，但老 tail 的 `next` 还没指向新节点」。所以从 `node.next` 找可能漏。反向遍历 `prev` 是安全的，因为 `prev` 在入队时就 CAS 好了。

## 面试场景 7：共享模式 acquireShared / releaseShared

🧑‍💻 你

共享模式和独占的关键区别：**获取到资源后要「传播」唤醒后继**，因为可能还剩资源可分配给下一个等待者。

```
public final void acquireShared(int arg) {
if (tryAcquireShared(arg) < 0)               // 返回负数 = 失败
doAcquireShared(arg);
}

private void doAcquireShared(int arg) {
// 类似独占，但获取成功后调 setHeadAndPropagate
}

private void setHeadAndPropagate(Node node, int propagate) {
Node h = head;
setHead(node);
// 如果还有剩余资源 or 前 head 是 PROPAGATE/SIGNAL → 继续唤醒后继
if (propagate > 0 || h == null || h.waitStatus < 0 ...) {
Node s = node.next;
if (s == null || s.isShared()) doReleaseShared();
}
}
```

`tryAcquireShared` 返回值的语义：

- < 0：失败

- = 0：成功但没剩余，不必唤醒后继

- > 0：成功且还有剩余，需唤醒后继

**Semaphore**（信号量）的 `tryAcquireShared` 返回「剩余许可数」；**CountDownLatch** 的 `tryAcquireShared` 返回 state==0 ? 1 : -1（0 时门打开）。

追问 PROPAGATE 状态为什么存在？

解决**共享模式下的唤醒信号丢失**问题。JDK 6 时代有个 bug：极端场景下 `releaseShared` 到一半，head 已经被新 acquire 换成新节点，导致后续该唤醒的线程被漏。PROPAGATE 是补丁：如果 release 时发现 head 的 waitStatus 是 0，改成 PROPAGATE；`setHeadAndPropagate` 里判断 `h.waitStatus < 0` 就会继续唤醒后继 —— 保证「至少有过一次 release」的信号不丢。

## 面试场景 8：AQS 的著名应用（一图看懂）

同步器模式state 语义典型用途

`ReentrantLock`独占重入计数可重入互斥锁
`ReentrantReadWriteLock`独占 + 共享高 16 位 = 读计数，低 16 位 = 写计数读写分离锁
`Semaphore`共享剩余许可数限流、连接池
`CountDownLatch`共享一次性倒计数「等 N 个任务全部完成再走」
`ThreadPoolExecutor.Worker`独占0/1标记 Worker 是否忙碌（不可重入）
`CyclicBarrier`——基于 ReentrantLock+Condition（不直接继承 AQS）

## 面试场景 9：公平锁 vs 非公平锁在 AQS 里的实现

🧑‍💻 你

差别只在 `tryAcquire` 的一行判断：

```
// 公平锁：先检查有没有前面的排队者，没有再 CAS
final boolean tryAcquire(int acquires) {
Thread current = Thread.currentThread();
int c = getState();
if (c == 0) {
if (!hasQueuedPredecessors() &&                    // ← 关键这行
compareAndSetState(0, acquires)) {
setExclusiveOwnerThread(current);
return true;
}
} else if (current == getExclusiveOwnerThread()) {      // 重入
setState(c + acquires);
return true;
}
return false;
}

// 非公平锁：进来直接 CAS 抢，不管队列有没有人等
final boolean nonfairTryAcquire(int acquires) {
Thread current = Thread.currentThread();
int c = getState();
if (c == 0) {
if (compareAndSetState(0, acquires)) {              // ← 直接 CAS
setExclusiveOwnerThread(current);
return true;
}
} else if (current == getExclusiveOwnerThread()) {
setState(c + acquires);
return true;
}
return false;
}
```

公平锁的代价：*吞吐显著下降*，因为每次都要检查队列，且总是让最先来的（可能已经 park 了）先拿 —— 上下文切换多。非公平锁允许「插队」，减少切换。`ReentrantLock` 默认非公平；`Semaphore` 也默认非公平。

## 面试场景 10：Condition 内部机制 & 与 wait/notify 对比

🧑‍💻 你

AQS 还提供 `ConditionObject`（AQS 的内部类），是 `Condition` 的官方实现。每个 Condition 维护**一条独立的 waitQueue**（单向链表），复用 Node 的 `nextWaiter` 指针。

`await` 流程：

1. 把当前线程包成 Node，加入 Condition 的 waitQueue 尾部

2. 完全释放锁（`fullyRelease`，处理可重入）

3. `LockSupport.park` 挂起

4. 被 `signal` 唤醒 → Node 从 waitQueue 转移到 CLH 尾部排队

5. 正常走 `acquireQueued` 重新获取锁

`signal` 流程：只把 waitQueue 头节点转移到 CLH 尾部，*不立刻唤醒线程* —— 等它排到 CLH 的 head 前面自然被 unpark。

对比`Object.wait/notify``Condition`

底层依赖Monitor (synchronized)ReentrantLock (AQS)
条件队列数量一个（对象自带 waitSet）**可多个**（一个 Lock 派生多个 Condition）
唤醒粒度粗（notify 随机；notifyAll 全部）细（不同条件挂不同 Condition 上）
响应中断都支持支持，且 `awaitUninterruptibly` 可选不响应
使用位置必须在 synchronized 块内必须在 `lock.lock()` 之后

典型例子：`ArrayBlockingQueue`（0017 课）就用了同一把 `ReentrantLock` 派生的两个 Condition —— `notEmpty`（唤醒 take）和 `notFull`（唤醒 put），比 `wait/notify` 的粗粒度精细多了。

## 💻 代码验证

### 验证 1：基于 AQS 手写一个不可重入互斥锁

```
import java.util.concurrent.locks.AbstractQueuedSynchronizer;

public class SimpleLock {
// AQS 子类：state=0 未持有，state=1 已持有
private static class Sync extends AbstractQueuedSynchronizer {
@Override
protected boolean tryAcquire(int arg) {
if (compareAndSetState(0, 1)) {
setExclusiveOwnerThread(Thread.currentThread());
return true;
}
return false;
}
@Override
protected boolean tryRelease(int arg) {
if (getState() == 0) throw new IllegalMonitorStateException();
setExclusiveOwnerThread(null);
setState(0);
return true;
}
@Override
protected boolean isHeldExclusively() {
return getState() == 1;
}
}

private final Sync sync = new Sync();
public void lock()   { sync.acquire(1); }
public void unlock() { sync.release(1); }

public static void main(String[] args) throws Exception {
SimpleLock lock = new SimpleLock();
int[] counter = {0};
Thread[] ts = new Thread[8];
for (int i=0;i<ts.length;i++) ts[i] = new Thread(() -> {
for (int j=0;j<100_000;j++) {
lock.lock();
try { counter[0]++; } finally { lock.unlock(); }
}
});
for (Thread t : ts) t.start();
for (Thread t : ts) t.join();
System.out.println(counter[0]);   // 800000 精确
}
}
```

### 验证 2：Semaphore 限流（AQS 共享模式的典型应用）

```
import java.util.concurrent.Semaphore;

public class RateLimit {
public static void main(String[] args) throws Exception {
Semaphore sem = new Semaphore(3);       // 最多 3 个并发

for (int i = 0; i < 10; i++) {
int id = i;
new Thread(() -> {
try {
sem.acquire();              // AQS.acquireShared
System.out.println(id + " running...");
Thread.sleep(1000);
} catch (InterruptedException e) { Thread.currentThread().interrupt(); }
finally { sem.release(); }      // AQS.releaseShared
}).start();
}
}
}
```

### 验证 3：CountDownLatch 汇合等待

```
import java.util.concurrent.CountDownLatch;

CountDownLatch latch = new CountDownLatch(3);

for (int i = 0; i < 3; i++) {
int id = i;
new Thread(() -> {
try { Thread.sleep(500 + id * 100); } catch (Exception e) {}
System.out.println("worker " + id + " done");
latch.countDown();                       // AQS state--
}).start();
}

latch.await();                                   // 阻塞直到 state==0
System.out.println("all done!");
```

### 验证 4：Condition 精细唤醒（对比 wait/notify）

```
import java.util.concurrent.locks.*;

ReentrantLock lock = new ReentrantLock();
Condition notEmpty = lock.newCondition();
Condition notFull  = lock.newCondition();

Object[] items = new Object[10];
int count = 0, putIdx = 0, takeIdx = 0;

// 生产者
lock.lock();
try {
while (count == items.length) notFull.await();      // 满 → 只挂到 notFull
items[putIdx] = "X";
if (++putIdx == items.length) putIdx = 0;
count++;
notEmpty.signal();                                   // 精准唤醒 take 者
} finally { lock.unlock(); }

// 消费者
lock.lock();
try {
while (count == 0) notEmpty.await();                // 空 → 只挂到 notEmpty
Object x = items[takeIdx];
if (++takeIdx == items.length) takeIdx = 0;
count--;
notFull.signal();                                    // 精准唤醒 put 者
} finally { lock.unlock(); }
```

## 🧠 自测

Self-Quiz · 合上课件再答

<details>

<summary>Q1 AQS 的三大核心是什么？</summary>

`volatile int state`（同步状态）+ CLH 双向队列（等待线程）+ 模板方法（`tryAcquire/tryRelease` 等钩子由子类实现）。

</details>

<details>

<summary>Q2 waitStatus 有哪几种值？SIGNAL 是「谁的」状态？</summary>

5 种：0（初始）、SIGNAL=-1（后继需被唤醒）、CANCELLED=1（已取消）、CONDITION=-2（在条件队列）、PROPAGATE=-3（共享传播）。SIGNAL 是**「前驱对后继的承诺」**—— 前驱释放锁时要 unpark 后继。

</details>

<details>

<summary>Q3 独占 acquire 失败后如何被阻塞？被唤醒后又怎么走？</summary>

失败 → `addWaiter` 入队；`acquireQueued` 自旋，把前驱状态置 SIGNAL；`LockSupport.park` 挂起。被前驱 `release → unparkSuccessor` 唤醒后，继续自旋 `tryAcquire`，成功就把自己设为 head。

</details>

<details>

<summary>Q4 `ReentrantReadWriteLock` 怎么用一个 int state 表示两个状态？</summary>

位分割：**高 16 位存读锁持有数、低 16 位存写锁持有数**。`tryAcquire/tryAcquireShared` 通过 `state & 0xFFFF`（写）和 `state >>> 16`（读）分离。所以最大只能支持 65535 个读锁 / 65535 次写锁重入。

</details>

<details>

<summary>Q5 Condition 相比 `Object.wait/notify` 好在哪？</summary>

最大优势：**一个 Lock 可以派生多个 Condition**，实现精细唤醒（如 ABQ 分离 `notEmpty` 和 `notFull`）；此外 Condition 支持不响应中断的 `awaitUninterruptibly`、超时 `awaitNanos`、绝对时间 `awaitUntil`。

</details>
