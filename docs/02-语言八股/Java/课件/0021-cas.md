# 0021 · 乐观锁 vs 悲观锁 & CAS & ABA

这一课把两篇  合并：与 。CAS 是 Java 无锁并发的基石 —— **Atomic 家族、AQS、ConcurrentHashMap 全都建立在它上面**。理解了 CAS，才能理解后面 0022 (Atomic)、0023 (AQS)、0024 (ReentrantLock) 是怎么长出来的。

## 学前热身

Warm-up · 凭直觉答一下

<details>

<summary>Q0.1 数据库的 `SELECT ... FOR UPDATE` 是乐观锁还是悲观锁？</summary>

**悲观锁**。读的时候就直接加行锁，其他事务动不了 —— 假设「一定会冲突」所以提前占位。乐观锁的 DB 实现是 `UPDATE ... WHERE version=?`。第 1、2 题细讲。

</details>

<details>

<summary>Q0.2 CAS 的 ABA 问题怎么解决？</summary>

用 `AtomicStampedReference` 加版本号 —— 每次修改版本号 +1，即使值从 A → B → A，版本号也不同，CAS 就能识别中间发生过变化。第 7 题细讲。

</details>

## 面试场景 1：悲观锁的思想和实现

🎤 面试官

什么是悲观锁？给一些典型的例子。

🧑‍💻 你

**悲观锁**：假设「共享资源每次被访问都会出现冲突」，所以*每次都提前加锁*。同一时刻只有一个线程能进入临界区，其他人阻塞等待。

Java 里的悲观锁：

- `synchronized`（JVM 内置，独占重量级/轻量级）

- `ReentrantLock`（JUC 显式锁，可中断、可公平、可 tryLock）

- `ReentrantReadWriteLock`（读读共享，读写/写写互斥）

数据库里的悲观锁：

- `SELECT ... FOR UPDATE`（InnoDB 行锁，直到事务提交才释放）

- `LOCK TABLES ... WRITE`（表级锁，粒度粗）

## 面试场景 2：乐观锁的思想和实现

🧑‍💻 你

**乐观锁**：假设「冲突很少发生」，所以*不加锁*，只在提交修改时校验：如果发现被别人改过，就重试或失败。

两种典型实现：

1. **版本号机制**（DB 常用）：给表加 `version` 字段，UPDATE 时带条件校验。

```
-- 线程读到 version=1
SELECT balance, version FROM account WHERE id=1;
-- 更新时校验
UPDATE account SET balance=100, version=version+1
WHERE id=1 AND version=1;
-- 若 affected rows=0 说明有人先改了，重试或报错
```

2. **CAS 算法**（Java 常用）：Compare-And-Swap 原子指令 —— 只有当前值等于期望值时才更新。`AtomicInteger` 全家、AQS 的 state 都是。

追问 乐观锁一定比悲观锁性能好吗？

不一定，取决于**冲突频率**。低冲突场景下乐观锁完胜（无阻塞、无上下文切换）；*高冲突场景下反而不如悲观锁* —— CAS 一直失败会疯狂重试烧 CPU；而悲观锁的线程阻塞是「休息」，CPU 让给别人用。

陷阱 「乐观锁不加锁」是简化说法。CAS 底层其实*要靠 CPU 层的 `lock` 前缀锁总线/缓存行*，只是没有 OS 层的互斥量而已。「无锁」指的是没有传统的 mutex，而不是真的没有任何同步开销。

## 面试场景 4：CAS 是什么？（★核心）

🎤 面试官

你说 CAS 是无锁并发的基础，具体是什么？

🧑‍💻 你

**CAS = Compare And Swap**。它是 CPU 提供的原子指令，接收三个操作数：

- **V**：内存地址（要修改的变量）

- **A**：预期原值（我以为 V 现在是什么）

- **B**：新值（想改成什么）

**语义**：「如果 V 当前值等于 A，就把它更新为 B；否则什么都不做，并返回 false」—— 这一整个「比较+更新」是*原子的*，别的线程无法插进来。

```
// 伪代码（其实由 CPU 指令保证原子）
boolean cas(V, A, B) {
if (*V == A) { *V = B; return true; }
else return false;
}
```

在 x86 上对应指令是 `cmpxchg`，多核情况下前面加 `lock` 前缀锁住总线或缓存行。ARM 用 `ldrex/strex`。

## 面试场景 5：Java 中 CAS 的实现

🧑‍💻 你

Java 层的入口是 `sun.misc.Unsafe` 类：

```
// JDK 8
public native boolean compareAndSwapInt(Object o, long offset, int expected, int x);
public native boolean compareAndSwapLong(Object o, long offset, long expected, long x);
public native boolean compareAndSwapObject(Object o, long offset, Object expected, Object x);
```

JDK 9+ 官方推荐 `VarHandle`（更安全、支持更多内存序）：

```
VarHandle vh = MethodHandles.lookup()
.findVarHandle(MyClass.class, "value", int.class);
vh.compareAndSet(instance, expected, newVal);
```

`AtomicInteger.getAndAdd` 的实现就是 CAS 自旋：

```
public final int getAndAddInt(Object o, long offset, int delta) {
int v;
do {
v = getIntVolatile(o, offset);
} while (!compareAndSwapInt(o, offset, v, v + delta));
return v;
}
```

## 面试场景 6：CAS 的三大问题（★经典）

1. **ABA 问题**：值从 A 变到 B 再变回 A，CAS 看着还是 A 就以为没变。下一题细讲。

2. **循环时间长开销大**：高竞争下 CAS 一直失败一直重试，白烧 CPU。JVM 会用 `pause` 指令（`Thread.onSpinWait()`）稍微歇一下减轻流水线压力，但根治办法是分片竞争（LongAdder）或退化到阻塞锁。

3. **只能保证一个共享变量的原子性**：CAS 一次只能改一个变量。要原子改两个必须封装成一个对象引用用 `AtomicReference`，或者退回到 `synchronized`。

## 面试场景 7：ABA 问题详解 & 解决方案（★经典）

🎤 面试官

ABA 问题在什么场景下会真的出问题？

🧑‍💻 你

纯数值场景 ABA 一般无害（`i` 从 5→10→5，其实业务上就是「等于 5」）。**但对象池/链表节点复用**时会翻车。

经典例子：无锁栈 pop。

```
// 无锁栈的 pop 实现
Node oldHead = top.get();
Node newHead = oldHead.next;
top.compareAndSet(oldHead, newHead);   // ← 隐患
```

假设初始栈 `A → B → C`，线程 T1 读到 `oldHead = A, newHead = B`，还没执行 CAS 就切走了。此时 T2 完整执行 `pop A`、`pop B`、`push A`（对象复用），栈变成 `A → C`。T1 回来 CAS 看 top 还是 A，成功 —— 但把 top 改成了*已经被删掉的 B*！栈直接损坏。

**解决方案：`AtomicStampedReference`** 每次 CAS 都带一个「版本戳」：

```
AtomicStampedReference<Node> top = new AtomicStampedReference<>(A, 0);

// pop
int[] stampHolder = new int[1];
Node oldHead = top.get(stampHolder);
int oldStamp = stampHolder[0];
Node newHead = oldHead.next;
top.compareAndSet(oldHead, newHead, oldStamp, oldStamp + 1);
// ↑ 就算引用相同，版本号不同也 CAS 失败
```

另一个变体是 `AtomicMarkableReference`，用 boolean 标记而非版本号 —— 适合「只要改过就标记，不关心改了几次」的场景。

## 面试场景 8：CAS 自旋 vs 阻塞的权衡

🧑‍💻 你

CAS 自旋是「乐观地重试」，加锁阻塞是「悲观地让路」。选谁取决于**预期临界区多长 + 竞争多激烈**：

- **临界区极短（几十纳秒） + 竞争少**：CAS 完胜 —— 不用上下文切换（约 1-5μs）。

- **临界区长 or 竞争激烈**：CAS 一直空转烧 CPU 不如阻塞让别人用 CPU。

- **介于中间**：JVM 有*自适应自旋* —— synchronized 在轻量级锁阶段会先自旋一小段再决定是否升级到重量级锁；ReentrantLock 的 AQS 也是「先短自旋再 park」。

JDK 之所以推出 `LongAdder`，就是为了缓解 `AtomicLong` 在高并发下的 CAS 竞争 —— 把一个热点变量分散到多个 Cell 上，每线程只 CAS 自己的 Cell，读时求和。下一课 0022 深挖。

追问 synchronized 和 CAS 谁快？

没有单一答案：*低竞争 CAS 完胜*（JDK 8 前的 Atomic 就是这么起家的）；*高竞争 synchronized 反而更好*（阻塞省 CPU + JDK 6+ 优化过的偏向/轻量级锁很轻）。这也是 JDK 15 弃用偏向锁（JEP 374）的原因之一 —— 现代应用几乎都是多线程，偏向锁的收益已经不足以抵消它的复杂度。

## 面试场景 9：手写一个基于 CAS 的自旋锁

```
import java.util.concurrent.atomic.AtomicReference;

public class SpinLock {
private final AtomicReference<Thread> owner = new AtomicReference<>();

public void lock() {
Thread me = Thread.currentThread();
while (!owner.compareAndSet(null, me)) {
Thread.onSpinWait();      // JDK 9+ 的 pause 提示
}
}

public void unlock() {
Thread me = Thread.currentThread();
owner.compareAndSet(me, null);
}
}

// 使用
SpinLock lock = new SpinLock();
lock.lock();
try { /* 临界区 */ } finally { lock.unlock(); }
```

这是最朴素的 CAS 用法。真正的 `ReentrantLock` 底层的 AQS 用 CAS 抢 state 后就 `park` 阻塞，不是纯自旋，避免烧 CPU。下一课 0022 和 0023 会讲。

## 面试场景 10：CAS 在 JUC 的应用全景

🧑‍💻 你

- **Atomic 家族**：`AtomicInteger`/`AtomicLong`/`AtomicReference`/`LongAdder` —— CAS 直接封装（下一课）

- **AQS**：`state` 字段的更新用 CAS，CLH 队列入队用 CAS `compareAndSetTail`（0023 课）

- **ConcurrentHashMap**：`put` 时桶为空 CAS 直接放；`size` 用 `CounterCell` CAS 分片计数（0015 课已讲）

- **线程池 `ThreadPoolExecutor`**：`ctl`（状态 + 工作线程数打包成一个 int）用 CAS 更新（0026 课）

- **StampedLock**：JDK 8+ 的乐观读锁 —— `tryOptimisticRead` 拿一个戳，读完 `validate(戳)` 校验期间没写过

### 验证 1：AtomicInteger 的 CAS 行为观察

```
import java.util.concurrent.atomic.AtomicInteger;

public class CasDemo {
public static void main(String[] args) {
AtomicInteger n = new AtomicInteger(10);

boolean r1 = n.compareAndSet(10, 20);   // ✅ 期望 10 → 更新为 20
boolean r2 = n.compareAndSet(10, 30);   // ❌ 现在是 20，期望 10 → 失败
System.out.println(r1 + " / " + r2 + " → n=" + n.get());
// true / false → n=20
}
}
```

### 验证 2：多线程 AtomicInteger vs 普通 int 对比

```
import java.util.concurrent.atomic.AtomicInteger;

class Counter {
volatile int plain = 0;
AtomicInteger atomic = new AtomicInteger(0);
}

public class Bench {
public static void main(String[] args) throws Exception {
Counter c = new Counter();
int threads = 8, times = 1_000_000;

Thread[] ts = new Thread[threads];
for (int i = 0; i < threads; i++) {
ts[i] = new Thread(() -> {
for (int j = 0; j < times; j++) {
c.plain++;              // ← 会丢失更新
c.atomic.incrementAndGet();
}
});
}
for (Thread t : ts) t.start();
for (Thread t : ts) t.join();

System.out.println("plain  = " + c.plain);       // 远小于 8*1M
System.out.println("atomic = " + c.atomic.get()); // = 8_000_000 精确
}
}
```

### 验证 3：ABA 问题演示 & AtomicStampedReference 修复

```
import java.util.concurrent.atomic.*;

public class AbaDemo {
public static void main(String[] args) throws InterruptedException {
// 普通 AtomicReference：ABA 隐患
AtomicReference<Integer> ref = new AtomicReference<>(100);
new Thread(() -> {
ref.compareAndSet(100, 200);
ref.compareAndSet(200, 100);   // 又变回 100
}).start();
Thread.sleep(100);
boolean ok = ref.compareAndSet(100, 999);   // 感知不到中间变化
System.out.println("Naive CAS: " + ok);      // true

// AtomicStampedReference：带版本号
AtomicStampedReference<Integer> sref = new AtomicStampedReference<>(100, 0);
new Thread(() -> {
int[] holder = new int[1];
Integer v = sref.get(holder);
sref.compareAndSet(v, 200, holder[0], holder[0] + 1);
v = sref.get(holder);
sref.compareAndSet(v, 100, holder[0], holder[0] + 1);
}).start();
Thread.sleep(100);
boolean ok2 = sref.compareAndSet(100, 999, 0, 1);   // 期望版本 0 已过时
System.out.println("Stamped: " + ok2);       // false ← 成功检测到 ABA
}
}
```

## 🧠 自测

Self-Quiz · 合上课件再答

<details>

<summary>Q1 用一句话概括乐观锁 vs 悲观锁的核心区别。</summary>

悲观锁「先加锁再操作」，假设冲突频繁；乐观锁「先操作提交时校验」，假设冲突罕见。

</details>

<details>

<summary>Q2 CAS 的三个操作数是什么？返回什么？</summary>

V（内存地址）、A（期望原值）、B（新值）。当 `*V == A` 时原子地把 `*V` 改为 B，返回 `true`；否则不动，返回 `false`。整个「比较+更新」由 CPU 指令保证原子。

</details>

<details>

<summary>Q3 CAS 有哪三大问题？分别怎么应对？</summary>

① ABA → `AtomicStampedReference`；② 自旋耗 CPU → 分片（LongAdder）或退化到阻塞锁；③ 只能保证单变量 → `AtomicReference` 封装多变量或用 `synchronized`。

</details>

<details>

<summary>Q4 ABA 问题在链表/对象池场景为什么会真出问题？</summary>

对象引用被回收再复用时，两次「相同引用」中间可能发生了删除-重建，链表结构已经被破坏，CAS 却看不到这个变化，会把指针指向不该指的地方。

</details>

<details>

<summary>Q5 LongAdder 相比 AtomicLong 快在哪里？</summary>

**分片 CAS** —— 把一个热点变量分散到多个 Cell，每线程按哈希落到不同 Cell 上 CAS，减少竞争；读时把 base + 所有 Cell 求和。空间换时间。（详见下一课 0022）

</details>
