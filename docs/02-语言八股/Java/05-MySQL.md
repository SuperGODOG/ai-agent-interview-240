# 05 · MySQL

## 一、存储引擎

- InnoDB（默认）：支持事务、行级锁、外键、MVCC；数据按主键聚簇存放（聚簇索引即数据文件）。
- MyISAM：不支持事务、只支持表锁、崩溃恢复差、索引和数据分离（非聚簇）。
- 选型：需要事务/并发写 → InnoDB；纯读归档场景才考虑 MyISAM，实际现代版本基本都用 InnoDB。

## 二、索引（必考）

### 为什么用 B+ 树
- 二叉树太深（IO 次数 = 树高）；B 树节点存数据，单节点存指针少，树更高；B+ 树：
  1. 非叶子节点只存索引键，不存数据 → 单节点可存上千个键，树矮（3~4 层），磁盘 IO 少。
  2. 叶子节点用双向链表串联 → 范围查询高效，全表扫描顺序读。
  3. 叶子节点才存数据，查询性能稳定（都是树高次 IO）。
- 为什么不用 Hash 索引：等值查询 O(1) 快，但不支持范围查询、排序、最左前缀，且哈希冲突。

### 聚簇索引 vs 非聚簇索引（二级索引）
- 聚簇：主键索引，叶子节点存整行数据；表数据物理顺序按主键。
- 非聚簇：叶子节点存主键值（回表查一次）；覆盖索引则无需回表。
- 为什么二级索引存主键而不是行指针：主键稳定，数据移动（页分裂）不影响二级索引。

### 覆盖索引
- 查询列都在索引里，无需回表。优化手段：select 只取需要的列，建联合索引覆盖。

### 联合索引最左前缀
- 联合索引 (a,b,c)：走 a、a,b、a,b,c；跳过 a 或跳列则部分失效/全失效。
- 原理：B+ 树先按 a 排序，a 相同再按 b，b 相同再按 c。

### 索引失效场景（必背）
1. 违反最左前缀
2. 对索引列做函数运算/隐式类型转换（如 where a+1=2、varchar 列 = 数字）
3. like '%xx'（前导模糊）
4. or 条件里有非索引列
5. 索引列参与计算或字符串未加引号
6. 优化器判断全表扫描更快（数据量小/区分度低）
7. 范围查询后右侧的列失效（a > 1 and b = 2，b 不一定走）

### 其他
- 主键建议自增/有序：避免页分裂和 B+ 树频繁调整；不要用 UUID 作主键。
- 区分度：索引列重复太多不走；cardinality 高才值得建。
- 回表代价大 → 覆盖索引优化。

## 三、事务与隔离级别

### ACID
- 原子性（undo log）、一致性、隔离性（锁/MVCC）、持久性（redo log）。

### 并发问题
- 脏读：读到未提交数据。
- 不可重复读：同一查询两次结果不同（另一事务提交修改）。
- 幻读：同一查询两次行数不同（另一事务插入）。

### 隔离级别
1. 读未提交 READ UNCOMMITTED：可能脏读/不可重复读/幻读。
2. 读已提交 READ COMMITTED（Oracle 默认）：解决脏读，仍不可重复读/幻读。
3. 可重复读 REPEATABLE READ（MySQL 默认）：解决脏读、不可重复读；InnoDB 靠 MVCC + 间隙锁基本防幻读。
4. 串行化 SERIALIZABLE：全锁，最安全最慢。

### MVCC（必考）
- 快照读（普通 select）通过 undo log 版本链 + ReadView 实现：ReadView 记录活跃事务 id 列表（m_ids）、min_trx_id、max_trx_id、creator_trx_id；判断版本可见性。
- 可重复读：事务第一次快照读时生成 ReadView，之后复用（快照固定）→ 不可重复读被解决。
- 读已提交：每次快照读都生成新 ReadView。
- 幻读的残留：可重复读下普通 select 走快照看不到新插入，但如果用当前读（for update/update/delete）仍可能看到，需靠间隙锁/next-key lock 锁住范围。所以说"InnoDB 可重复读基本解决幻读"。

## 四、锁

- 全局锁（FTWRL，备份用）、表级锁（表锁、MDL 元数据锁、意向锁）、行级锁（记录锁 Record Lock、间隙锁 Gap Lock、临键锁 Next-Key Lock）。
- 意向锁：表级，表示"有事务准备/正在对表内某行加锁"，让表锁判断快速（不用扫全行）。
- 当前读 vs 快照读：select ... for update / lock in share mode / update / delete 是当前读（读最新+加锁）。
- 死锁：两个事务互相持有对方需要的锁 → 检测到死锁回滚代价小的事务（innodb_deadlock_detect=on）；避免：按固定顺序加锁、缩小锁范围、超时。
- 间隙锁：RR 下对不存在的记录范围加锁，防幻读；范围过大影响并发，可把隔离级别降到 RC 减少间隙锁。

## 五、日志（redo / undo / binlog）

- redo log：InnoDB 引擎层，物理日志（页修改），崩溃恢复用，WAL 先写日志再落盘，保证持久性。
- undo log：逻辑日志，回滚 + MVCC 版本链，保证原子性。
- binlog：Server 层，逻辑日志，主从复制和数据恢复用。
- 两阶段提交：redo log prepare → binlog 写入 → redo log commit，保证 binlog 与 redo 一致（崩溃恢复不会主从不一致）。

## 六、explain 与慢查询优化

### explain 关键字段
- type（访问类型，好→差）：system > const > eq_ref > ref > range > index > ALL（出现 ALL/index 要警惕）。
- key：实际使用的索引；key_len：用了索引的字节数；rows：预估扫描行数；Extra：Using index（覆盖）、Using filesort（文件排序，优化）、Using temporary（临时表，优化）、Using where。

### 慢查询优化步骤
1. 慢查询日志打开（long_query_time），捞 SQL。
2. explain 看 type/key/rows。
3. 优化方向：建/改索引（覆盖、联合）、避免索引失效、分页深翻页（延迟关联/游标）、避免 select *、拆大事务、必要时分表分库。

## 七、常问追问

1. 为什么 B+ 树比 B 树适合做索引？→ 非叶子不存数据→矮；叶子链表→范围查询。
2. 主键为什么用自增？→ 顺序插入避免页分裂。
3. 联合索引 (a,b,c)，where b=1 and a=2 走吗？→ 走（优化器可重排，等价 a,b 前缀）。
4. 可重复读怎么解决幻读？→ MVCC 快照 + 当前读的 next-key lock。
5. 什么场景索引会失效？→ 函数/隐式转换/前导模糊/or/违反最左。
6. 深分页 limit 100000,10 为什么慢？→ 先扫 100010 行再丢；用游标/延迟关联优化。
7. 一条 update 执行过程？→ 锁行 → 写 undo → 改内存 → 写 redo prepare → 写 binlog → redo commit → 刷盘。
8. 什么时候表锁/行锁？→ InnoDB 无索引条件会退化成全表扫描+表锁（实际是锁所有行）。
