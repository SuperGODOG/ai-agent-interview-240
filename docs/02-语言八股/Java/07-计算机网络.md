# 07 · 计算机网络

## 一、分层模型

- OSI 七层：物理 → 数据链路 → 网络 → 传输 → 会话 → 表示 → 应用。
- TCP/IP 四层：网络接口层 → 网络层（IP）→ 传输层（TCP/UDP）→ 应用层（HTTP/DNS/FTP）。
- 面试主要记：应用层、传输层、网络层、数据链路层各自的职责和协议。

## 二、TCP 三次握手（必考）

### 过程
1. 客户端 → SYN=1, seq=x（SYN_SENT）
2. 服务端 → SYN=1, ACK=1, seq=y, ack=x+1（SYN_RCVD）
3. 客户端 → ACK=1, seq=x+1, ack=y+1（ESTABLISHED）

### 为什么不是两次
- 两次握手无法确认"客户端接收能力"和"服务端发送能力"，且防止失效的旧 SYN 请求突然到达服务端建立空连接（半连接）。
### 为什么不是四次
- 三次已足够确认双方收发能力，四次冗余。
### SYN 洪水
- 攻击者只发 SYN 不完成握手，占满半连接队列；缓解：SYN Cookie（不分配资源，用 cookie 校验）。

## 三、TCP 四次挥手（必考）

### 过程
1. 主动方 → FIN=1（FIN_WAIT_1）
2. 被动方 → ACK（CLOSE_WAIT；主动方 FIN_WAIT_2）
3. 被动方数据发完 → FIN=1（LAST_ACK）
4. 主动方 → ACK（TIME_WAIT，2MSL 后 CLOSED）

### 为什么 TIME_WAIT 要 2MSL
1. 保证最后一个 ACK 能到达（丢失则对方重发 FIN，我方还能回应）。
2. 让本连接产生的旧报文在网络中自然消亡，防止污染新连接。
- MSL：报文最大生存时间；2MSL = 一来一回最坏时间。
- 大量 TIME_WAIT 出现在主动关闭方（服务端常见），优化：长连接复用、调整 tcp_tw_reuse。

## 四、TCP vs UDP

| TCP | UDP |
| --- | --- |
| 面向连接 | 无连接 |
| 可靠（确认、重传、排序） | 不可靠，尽力而为 |
| 流量控制、拥塞控制 | 无 |
| 字节流 | 报文 |
| 效率低 | 效率高、延迟低 |

- 应用：TCP（HTTP、文件传输、数据库）；UDP（视频通话、游戏、DNS、QUIC 底层）。

## 五、TCP 可靠传输与拥塞控制

### 可靠机制
- 序号 + 确认应答（ACK）、超时重传、快速重传（收到 3 个重复 ACK）、滑动窗口（流量控制，窗口大小由接收方通告）、累计确认、SACK（选择性确认）。

### 拥塞控制（4 个算法）
1. 慢启动：cwnd 从 1 指数增长，到 ssthresh 转拥塞避免。
2. 拥塞避免：cwnd 线性增长。
3. 快重传：3 个重复 ACK 立即重传。
4. 快恢复：快重传后 cwnd 减半而非归 1（区别于超时重传）。
- 流量控制（接收方窗口 rwnd） vs 拥塞控制（网络拥塞窗口 cwnd）：前者管"对方能不能收"，后者管"网络能不能扛"。

## 六、HTTP

### 版本演进
- HTTP/1.0：短连接，一次请求一次连接。
- HTTP/1.1：持久连接（keep-alive）、管道化（有队头阻塞问题）、Host 头、分块传输。
- HTTP/2：二进制分帧、多路复用（一个连接并发多个流，仍存在 TCP 层队头阻塞）、头部压缩 HPACK、服务端推送。
- HTTP/3：基于 UDP + QUIC，解决 TCP 队头阻塞，0-RTT 建连。

### 请求方法
- GET（幂等、可缓存）、POST（非幂等）、PUT（整体更新，幂等）、PATCH（部分更新）、DELETE、HEAD、OPTIONS（预检请求）。

### 状态码（背常用）
- 200 OK；201 Created；204 No Content
- 301 永久重定向；302 临时重定向；304 Not Modified（协商缓存命中）
- 400 参数错误；401 未认证；403 禁止访问；404 不存在；405 方法不允许
- 500 服务器内部错误；502 Bad Gateway（网关/代理拿到无效响应）；503 服务不可用；504 网关超时

### HTTP 缓存
- 强缓存：Cache-Control（max-age）、Expires（绝对时间，有本地时钟问题）；命中 200 from cache，不发请求。
- 协商缓存：Last-Modified/If-Modified-Since、ETag/If-None-Match；命中返回 304。
- 顺序：先查强缓存，失效再协商。

## 七、HTTPS（必考）

### 为什么
- HTTP 明文：不加密、不防篡改、不验证身份。HTTPS = HTTP + TLS。

### 握手过程（简化）
1. 客户端发 ClientHello（支持的加密套件、随机数 A）。
2. 服务端回 ServerHello（选定套件、随机数 B）+ 证书（含公钥）+ 可选要求客户端证书。
3. 客户端验证证书（CA 链、域名、有效期、吊销）→ 生成预主密钥 premaster → 用服务端公钥加密发给服务端。
4. 双方用 随机数A + 随机数B + premaster 算出会话密钥（对称密钥）。
5. 之后业务数据用对称加密（AES）传输，完成握手（RSA 版本；TLS1.3 用 ECDHE 前向安全）。

### 关键点
- 非对称加密（RSA/ECDHE）只用于协商密钥和验证身份；对称加密（AES）用于业务数据，性能高。
- 证书/CA：证书是"公钥 + 身份信息"由 CA 私钥签名，客户端用内置 CA 公钥验签 → 防中间人。
- 前向安全：即使服务端私钥泄露，历史流量也解不开（用 ECDHE 临时密钥对）。
- 中间人攻击为什么 HTTPS 能防：伪造证书过不了 CA 校验。

## 八、DNS 与常用概念

- 解析过程：浏览器缓存 → 系统 hosts → 本地 DNS 服务器（递归）→ 根服务器 → 顶级域（.com）→ 权威服务器（迭代）。
- CDN：内容分发网络，就近返回缓存节点；回源机制。
- 负载均衡：四层（IP+端口，LVS）vs 七层（HTTP，Nginx）。

## 九、常问追问

1. 为什么挥手要四次而握手三次？→ 握手可捎带 ACK+SYN；挥手时被动方可能还有数据要发，ACK 和 FIN 分开发。
2. TIME_WAIT 过多会怎样？→ 端口被占用，新连接失败；服务端优化思路。
3. TCP 粘包是什么，怎么解决？→ 字节流无边界；固定长度/分隔符/长度字段（自定义协议）。
4. HTTP/1.1 队头阻塞是什么？→ 同一连接请求必须按序响应。
5. 输入 URL 到页面显示发生了什么？→ DNS → TCP → TLS → HTTP 请求 → 服务器处理 → 响应渲染（常考连环问）。
6. GET 和 POST 区别？→ 语义、幂等、参数位置（body/url）、缓存。
7. 304 流程？→ 协商缓存命中返回 304，客户端用本地缓存。
8. 证书链校验怎么做的？→ 自底向上用上级公钥验签，直到信任根。
