# 10 · 高并发锁：秒杀 / 超卖 / 幂等 / 限流

## 一、超卖问题（必考）

### 问题本质
- 并发扣库存时"先查再改"有竞态：两个请求都读到库存=1，都减到 0，实际卖出 2 件 → 超卖。
- 根因：读-判断-写不是原子操作，或锁没覆盖整个判断+扣减。

### 解决思路（从简单到复杂）

1. SQL 原子扣减（最简单可靠）：
```sql
UPDATE stock SET stock = stock - 1 WHERE id = ? AND stock > 0;
```
- 数据库行锁保证原子，affected rows = 0 说明没库存。一个语句搞定，不加应用层锁。
- 要求：必须带上 `stock > 0` 条件（条件更新），否则仍会扣成负数。

2. 乐观锁（版本号）：
```sql
UPDATE stock SET stock = stock - 1, version = version + 1
WHERE id = ? AND version = ?;
```
- 适合冲突少的场景；冲突多则大量重试，不如下面悲观锁直接。

3. 悲观锁（行锁）：
```sql
SELECT stock FROM stock WHERE id = ? FOR UPDATE;  -- 锁住该行
-- 业务判断 + 扣减
```
- 保证同一行串行，但要等锁，且必须在事务里，避免锁被长事务持有。

4. 分布式锁（多实例/集群场景）：
- 同一商品同一把 Redis/ZK 锁，串行执行扣减；但吞吐低，秒杀一般不靠它挡流量（详见"分布式锁"小节）。

### 秒杀场景为什么不直接对 DB 加锁
- 秒杀流量几十万 QPS，DB 锁扛不住；正确姿势是"前置拦截 + 分层削峰"（下面整体设计）。

## 二、秒杀系统整体设计（高频场景题）

### 核心思想：让大部分请求在数据库之前就被挡住
1. 静态化 + CDN：商品详情页静态化，动态数据单独接口；静态资源走 CDN，扛大流量。
2. 前端拦截：按钮置灰、答题/验证码、限频（同一用户 N 秒一次）。
3. 网关限流：按用户/IP/接口 QPS 限流（令牌桶），超出的直接返回"抢完了"。
4. 提前资格校验：Redis 预扣/资格标记（setnx 每人限购 1 件），不合格直接拒绝，不打 DB。
5. Redis 原子扣库存（Lua 脚本）：`if stock > 0 then stock-1 else return 0`，Redis 单线程保证原子；抢到才生成订单。
6. 异步下单（MQ 削峰）：抢到资格 → 发消息 → 订单服务慢慢消费落库；用 Redis 的库存作为"挡板"，DB 库存与 Redis 库存最终一致（对账）。
7. 接口防刷：令牌/签名、风控、频控。
8. 降级/兜底：MQ 积压监控、库存对账任务（Redis 与 DB 不一致时补偿）。

### 库存扣减的"双写一致性"
- 下单前扣 Redis 库存（热路径），消费端扣 DB 库存（落库路径）；失败/回滚时补回库存；定时任务对账 Redis 与 DB。

### 为什么用 Redis 扣库存而不是 DB
- Redis 单线程 + 内存，Lua 原子操作，几十万 QPS 也能扛；DB 行锁在这个量级是瓶颈。

## 三、幂等性（必考）

### 定义
- 同一个请求执行一次和执行多次，效果一样（不重复下单、不重复扣款）。

### 为什么需要
- 网络重试、前端重复点击、MQ 重复消费、网关重发。

### 常见实现
1. 唯一业务号（订单号/请求号）：
   - 客户端生成请求 ID，服务端存已处理表（唯一索引）；重复请求命中索引则直接返回旧结果。
2. 数据库唯一约束：如表里 `user_id + sku_id` 唯一，重复插入报错捕获即可。
3. 状态机幂等：订单状态只能 已创建→已支付→已发货，已支付不会再次扣款。
4. Redis 去重：`SETNX key value` 成功才处理（带过期），失败返回已处理。
5. Token 令牌（防重复提交）：进入页面发 token，提交时校验并删除（Redis GETDEL），只允许一次。

### 与"防重"的区别
- 防重是前端/入口层，幂等是服务端保证；入口防重挡不住恶意/重试，服务端幂等才是底线。

## 四、限流（必考）

### 单机限流算法
1. 固定窗口计数器：1 分钟内最多 N 次；缺点：窗口边界双倍突发（59 秒和 01 秒各 N 次）。
2. 滑动窗口：把窗口切成小格，滑过时淘汰过期格；比固定窗口平滑。
3. 漏桶：请求进桶，恒定速率出水（处理）；流量整形，能平滑突发，但无法应对突发流量（满了直接丢）。
4. 令牌桶：按速率放令牌，桶容量限制突发；有令牌就放行，允许一定突发（最常用，Guava RateLimiter 就是令牌桶）。
- 选型：要平滑突发 → 令牌桶；要严格匀速 → 漏桶。

### 分布式限流
- Redis + Lua 实现滑动窗口/令牌桶（INCR + 过期，或 ZSet 记录时间戳）；开源：Sentinel、网关层（Nginx lua-resty-limit、Spring Cloud Gateway）。
- 限流维度：QPS、并发数（信号量）、用户/IP/接口/集群总量。

### 限流位置
- 网关（全局粗粒度）→ 应用层（接口级、方法级注解）→ 关键资源（DB/Redis 连接）。

## 五、分布式锁专题（必考）

### 为什么需要
- 多实例部署时，synchronized/本地锁只对本进程生效；跨进程要"同一把锁"，如定时任务只允许一台执行、库存扣减、缓存重建。

### 实现方案对比
| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| DB 唯一索引/`for update` | 实现简单 | 性能差、有单点 |
| Redis SETNX + Lua | 高性能 | 主从切换可能丢锁（极端） |
| ZooKeeper/etcd 临时顺序节点 | 强一致、自动释放（会话断开） | 性能低于 Redis、组件重 |
| Redisson | 封装好：看门狗续期、可重入 | 仍是 Redis 语义 |

### Redis 分布式锁标准实现（背）
1. 加锁：`SET lock:order:1001 uuid NX EX 30`（原子：不存在才设置 + 过期时间）。
2. 业务执行（超过 30s 会过期，需看门狗续期——Redisson 默认每 10s 续 30s）。
3. 解锁：Lua 脚本保证"先比较 value 再删除"：
```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```
- 为什么 value 要唯一（uuid/线程 id）：防止误删别人刚拿到的锁（锁过期后 B 拿到锁，A 的 del 把 B 的锁删了）。
- 为什么删除要用 Lua：比较和删除必须原子，两步走有窗口。
- 可重入：用 Hash 存 `{threadId: count}`，重入 count+1。
- RedLock（多个独立 Redis 节点过半加锁）：理论更强，但业界有争议（时钟跳跃、脑裂），一般业务用单主 + 看门狗即可，真需要强一致选 ZK/etcd。

### 分布式锁 vs 乐观锁怎么选
- 低冲突 + 可重试 → 乐观锁（版本号/条件更新）；
- 高冲突/要串行执行关键动作 → 分布式锁；
- 秒杀库存这种"单条条件更新" → 数据库原子 SQL 就够了，不加分布式锁。

## 六、常问追问

1. 库存扣减为什么一条 SQL 能防超卖？→ `stock > 0` 条件 + 行锁原子执行。
2. Redis 扣库存和 DB 扣库存谁准？→ DB 为准，Redis 挡流量，最终对账。
3. 秒杀为什么要异步？→ 削峰，保护 DB 和下游。
4. 幂等和防重有什么区别？→ 防重是入口优化，幂等是服务端保证。
5. 令牌桶和漏桶区别？→ 漏桶匀速整形、令牌桶允许突发。
6. 分布式锁 key 过期了但业务没执行完？→ 看门狗续期；或用 ZK 自动释放。
7. 为什么删除锁要用 Lua？→ 比较+删除必须原子。
8. 单机限流在集群下失效？→ 每台各自计数，总量超了；需要 Redis 限流或网关统一限流。
9. 超卖能不能完全避免？→ 正确实现条件更新 + 事务可以；但高并发下要分层设计。
10. 分布式锁和数据库唯一索引能互相替代吗？→ 不能：唯一索引适合幂等去重，锁适合互斥串行。
