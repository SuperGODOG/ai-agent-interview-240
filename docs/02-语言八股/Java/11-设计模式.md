# 11 · 设计模式：单例 / 工厂 / 代理 / 策略

## 一、单例模式（必考，手撕概率最高）

### 定义
- 一个类全局只有一个实例，提供全局访问点。

### 写法（由差到好）

1. 饿汉式（线程安全，但类加载即创建，可能浪费）：
```java
public class Singleton {
    private static final Singleton INSTANCE = new Singleton();
    private Singleton() {}
    public static Singleton getInstance() { return INSTANCE; }
}
```

2. 懒汉式（非线程安全，多线程会创建多个）：
```java
public class Singleton {
    private static Singleton instance;
    private Singleton() {}
    public static Singleton getInstance() {
        if (instance == null) instance = new Singleton(); // 竞态！
        return instance;
    }
}
```

3. 双重检查锁 DCL（推荐，高频手撕）：
```java
public class Singleton {
    private static volatile Singleton instance;
    private Singleton() {}
    public static Singleton getInstance() {
        if (instance == null) {                    // 第一次检查，避免每次加锁
            synchronized (Singleton.class) {
                if (instance == null) {            // 第二次检查，锁内再判空
                    instance = new Singleton();    // 为什么 volatile？见下
                }
            }
        }
        return instance;
    }
}
```

### 为什么双重检查锁要 volatile（必考核心）
- `instance = new Singleton()` 不是原子操作，JVM 可能重排为三步：
  1. 分配内存
  2. 执行构造（初始化对象）
  3. 把引用赋值给 instance
- 重排后可能变成 1 → 3 → 2：另一个线程第一次检查发现 `instance != null`，直接返回，但此时对象还没初始化完成（半初始化）→ 使用时报错或拿到脏数据。
- volatile 禁止该指令重排序（写 volatile 变量时插入 StoreStore 屏障），保证"对象完全构造完成"才对其他线程可见。
- 补充：volatile 还保证可见性——实例赋值对其他线程立即可见。

### 4. 静态内部类（推荐，最优雅）：
```java
public class Singleton {
    private Singleton() {}
    private static class Holder { static final Singleton INSTANCE = new Singleton(); }
    public static Singleton getInstance() { return Holder.INSTANCE; }
}
```
- 类加载时才初始化（懒加载），且类加载机制天然线程安全。

### 5. 枚举（最安全，防反射/序列化破坏）：
```java
public enum Singleton { INSTANCE }
```
- 反射不能 new 枚举、序列化天然单例；《Effective Java》推荐。

### 破坏单例与防御
- 反射：调用私有构造器创建第二个实例 → 防御：构造器里加标志位，第二次抛异常。
- 序列化：readObject 创建新实例 → 防御：实现 readResolve 返回同一实例。
- 枚举两者都天然防住。

### 应用
- 线程池、连接池、配置对象、Spring 的单例 Bean（容器管理，本质类似）。

## 二、工厂模式

### 三种形态
1. 简单工厂（不算 GoF 23 种，但常考）：
- 一个工厂类，根据参数返回不同产品：
```java
public static Product create(String type) {
    if ("A".equals(type)) return new ProductA();
    if ("B".equals(type)) return new ProductB();
    throw new IllegalArgumentException();
}
```
- 缺点：新增产品要改工厂（违反开闭原则）。

2. 工厂方法（对简单工厂的改进）：
- 每个产品对应一个工厂子类，新增产品只加类不改老代码：
```java
interface ProductFactory { Product create(); }
class ProductAFactory implements ProductFactory { public Product create() { return new ProductA(); } }
```

3. 抽象工厂：
- 创建"一族"相关产品（如不同风格 UI 的按钮+输入框），工厂返回一组产品；适合产品族扩展。

### 使用场景
- 把"创建对象"和"使用对象"解耦；JDK：Calendar.getInstance()、NumberFormat；Spring：BeanFactory 就是工厂模式（工厂方法）。

### 与构建者模式区别
- 工厂：用一个方法整体产出对象；Builder：分步骤设置属性最后 build（对象构造参数多时用）。

## 三、代理模式（必考，常结合 Spring AOP）

### 定义
- 不直接访问目标对象，通过代理控制访问：在调用前后增强（日志、权限、事务、缓存）。

### 静态代理
- 手写代理类，实现同一接口，持有目标对象引用：
```java
class UserServiceProxy implements UserService {
    private final UserService target;
    public void save() { log(); target.save(); }
}
```
- 缺点：每个类都要手写代理，代码重复。

### JDK 动态代理（必背）
- 要求目标实现接口；`Proxy.newProxyInstance(类加载器, 接口数组, InvocationHandler)`，所有调用进 invoke 方法：
```java
UserService proxy = (UserService) Proxy.newProxyInstance(
    target.getClass().getClassLoader(),
    target.getClass().getInterfaces(),
    (p, method, args) -> { log(); return method.invoke(target, args); });
```
- 为什么必须接口：生成的代理类 `$Proxy0` 只能 implements 接口（Java 单继承，不能继承任意目标类），靠接口协议转发。

### CGLIB 动态代理
- 目标没有接口时用；原理：字节码技术（ASM）生成目标类的子类，重写非 final 方法，方法调用走 MethodInterceptor。
- 限制：final 类/final 方法无法代理。

### JDK vs CGLIB（背对比）
| | JDK 动态代理 | CGLIB |
| --- | --- | --- |
| 要求 | 实现接口 | 无接口 |
| 原理 | 生成实现接口的代理类 | 生成目标子类 |
| 限制 | 无接口不能用 | final 类/方法不能代理 |
| 性能 | 高版本已优化 | 创建慢、调用快 |

### 应用
- Spring AOP 默认按"是否有接口"选 JDK/CGLIB（Boot 2.x 默认 CGLIB）；MyBatis Mapper 动态代理生成实现类；RPC/Feign 远程调用。

## 四、策略模式（常考 + 场景题）

### 定义
- 定义一族算法，分别封装，可以互相替换；客户端持有策略接口，运行时选择具体策略。
```java
interface DiscountStrategy { double discount(double price); }
class VipDiscount implements DiscountStrategy { ... }
class NormalDiscount implements DiscountStrategy { ... }

class OrderService {
    private DiscountStrategy strategy;            // 组合替代继承
    public double calc(double price) { return strategy.discount(price); }
}
```

### 与 if-else 的关系
- 策略模式的目标之一就是消除"一堆 if-else 选算法"的代码：不同分支封装成不同策略类，由工厂/Map 根据条件取策略。
- 典型落地：`Map<String, DiscountStrategy>`，key 是类型，注册时放进去，运行时 `map.get(type)` 直接拿，无需 if-else。

### 与状态模式的区别（高频追问）
- 策略：客户端主动选择算法，算法之间无依赖、可替换（同一行为不同做法）。
- 状态：对象内部状态变化驱动行为变化，状态之间会流转（如订单 待支付→已支付→已发货）。

### 使用场景
- 支付渠道选择（微信/支付宝/银联）、促销活动、第三方登录、解析器/校验器。

## 五、常问追问

1. DCL 为什么要 volatile？→ 禁指令重排，防半初始化对象（三步重排问题）。
2. 静态内部类和 DCL 哪个好？→ 静态内部类：由类加载机制保证线程安全、代码更少。
3. 枚举单例为什么最安全？→ 防反射、防序列化。
4. 简单工厂和工厂方法区别？→ 简单工厂一个类判断参数，工厂方法每个产品一个工厂，开闭原则更好。
5. JDK 动态代理为什么要求接口？→ 生成的代理类只能 implements 接口。
6. CGLIB 为什么不能代理 final？→ 通过继承生成子类，final 无法继承重写。
7. Spring 事务失效和代理有什么关系？→ 自调用不经过代理，所以 @Transactional 失效。
8. 策略模式和 if-else 有什么关系？→ 策略封装算法 + 工厂/Map 消除分支。
9. 什么时候用策略、什么时候用状态？→ 主动选算法 vs 状态流转。
10. 手写一个 DCL 单例（写完整）→ 见上文代码，注意 volatile 和私有构造器。
